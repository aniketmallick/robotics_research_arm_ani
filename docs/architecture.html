1 STT / TTS — and where Mistral fits

There are two ways to build a voice loop. The cascade: three separate workers passing notes — STT transcribes audio→text, an LLM thinks in text, TTS turns the reply into audio. Mistral's Voxtral (what the Cyberwave tutorial used) is an STT model — it's one third of that cascade, same job as Whisper.

The Realtime API collapses all three into one model: audio in → audio out. Faster (~0.5–0.8s vs ~1.5s), natural interruptions, and it never "mis-reads a transcript" because there is no transcript in the middle.

Cascade (3 parts)
mic → Voxtral/Whisper → GPT/Claude → ElevenLabs → speaker
+ cheap, modular, survives bad wifi with local Whisper · − slower, 3 things to wire
Realtime (1 part) ← we use this
mic → gpt-realtime-2.1 → speaker
+ fastest, barge-in, talks while arm moves · − pricier, needs internet

We build Realtime as primary and keep a cascade fallback (faster-whisper + gpt-4o-mini + TTS) in the back pocket for venue-wifi apocalypse.

2 The LLM — who understands and who acts

The Realtime model is the LLM — a GPT-class brain that happens to have ears and a mouth. You don't add another one for conversation.

How acting works: you register python functions as "tools." When you say "pick up the banana," the model doesn't move anything — it emits a tool call: pick("banana"). Your python code then runs the cameras, math, and motors, and returns a result ("gripped, verified ✅"). The model reads that result and speaks: "Banana secured. You're welcome." Brain decides, your code executes. Clean separation.

Claude appears once, as a specialist inside one tool: improvise_move() — it's good at writing structured JSON keyframes for novel gestures. Optional but a great party trick.

3 The VLM — the eyes, called on demand

The VLM is not in the conversation loop — it lives inside the see() and pick() tools. When called: your code snaps a C920 frame → sends it to Gemini Robotics-ER 1.6 (a Google model trained for robots — returns exact pixel points on named objects) → also runs OWLv2 locally (returns honest confidence scores per object). Results come back as text; the brain talks about them.

Why two? Gemini = best-in-class open-vocabulary pointing. OWLv2 = real probability numbers for the confidence gate (Gemini's self-reported confidence isn't calibrated). When they agree, confidence is high. When they disagree — that itself is a "low confidence, ask the human" signal.

Do NOT use GPT-4o for locating objects — it's documented to fail at bounding boxes. OpenAI runs the mouth; Gemini/OWLv2 run the eyes.

4 Recording vs training — two different things

Recording: yes (1 hour). Training: no (0 hours).

You'll record ~8 gesture episodes via teleop (you puppet the bow once with the leader arm; it's saved). But that's a macro — pressed play, executed identically every time, like a playlist. Zero machine learning involved.

Training (ACT/SmolVLA — showing a model 50 demos so it learns a behavior) is NOT needed for anything in the demo. Optional: run one ACT training on Colab overnight (~$3) purely as a "here's our roadmap with learned policies" slide. It never touches the live demo.

5 New object or new gesture at runtime — will it work?

New object → YES, and it's your best demo moment. Gemini and OWLv2 are open-vocabulary: they can find things nobody planned for. Ask a judge to put THEIR pen or phone-stand on the table and say "pick that up." Two caveats: it must physically fit the gripper top-down, and be inside reach — and if not, the trust gates catch it and the robot says so (which is the pitch!).

New gesture → recorded macros are fixed (only the 8 you made), but improvise_move() covers novel ones: "do a slow clap" → Claude writes keyframes → clamped → executed. Goofy but charming, and safe by construction.

The flip side — and why we don't train: a trained ACT policy is the OPPOSITE. It repeats the one task it learned, with the same camera angle, same-ish object positions. New object? Fails. Camera nudged 2cm? Fails. Our no-training stack generalizes; the trained stack memorizes.

6 ChArUco — what, why, and the "can't we just use the table?" answer

What: a printed checkerboard with QR-like markers. You show it to the camera once, flat on the table.

Why it exists: the camera says "banana at pixel (712, 419)." The robot needs "banana at (18cm, 12cm) from my base." Those are two different languages, and nothing in the system can translate without calibration — a single RGB camera has no depth, so a pixel alone doesn't pin a location. The saving trick: everything sits on ONE flat plane (the table). Given that, a single 3×3 matrix — the homography — converts any pixel to exact table coordinates. The board just gives OpenCV dozens of precisely-known points to compute that matrix in one shot. 10 minutes, done once. (If the camera gets bumped: redo, 5 min. So: tape the camera.)

Do you NEED the board? No — you need the matrix. Three ways to get pixel→cm, in order of preference:

A · ChArUco board
Print, place, one script. Most accurate, fastest. What Google's SO-101 sample uses.
B · Gripper-tip method (no printer)
Jog the gripper tip to 6 spots; record robot XY (from kinematics) + pixel of the tip; cv2.findHomography. 20 min, slightly less accurate.
C · Taught zones (no math at all)
5 marked spots, one recorded pick macro each. VLM only chooses WHICH zone. Guaranteed to work — the fallback if A/B fight you.
